# purser: repo design and spec review

Drop this file into the repo as `docs/DESIGN.md`. It reviews the GPT spec, scopes v1, and defines the structure and data conventions.

## Verdict on the GPT spec

The instincts are right and about 40% of it belongs in v1. The canonical data model, immutable raw layer, idempotent imports, FITID-plus-fingerprint dedupe, deterministic rules before AI, transfer matching, auditability chain, and "AI never does arithmetic" are all correct and worth keeping verbatim. That part reads like someone who has been burned by aggregator apps.

The rest is the over-architecting you said you hate, written in PRD voice. Taken literally it describes roughly six subsystems (reconciliation engine, net-worth engine, scenario modeler, recommendation engine with difficulty/confidence scoring, investment analytics, financial timeline, ops-console dashboard, web API). That is a year of evenings and it front-loads the parts you need least. Specific cuts:

- OFX/QFX as the preferred format does not match reality: NFCU dropped OFX/QFX in April 2026 (CSV and PDF only) and Schwab exports CSV/JSON/XML. Design around CSV adapters. Keep an OFX adapter stub for future institutions, do not build it first.
- Investment intelligence: v1 ingests Schwab transactions and balance snapshots so cash flow and net worth are right. Allocation, concentration, gains analysis is a later milestone. Do not touch cost basis until then.
- Recommendation engine with difficulty/risk/confidence scoring per action: this is what the AI layer already does conversationally against good tables. Do not build it as a subsystem.
- Scenario modeler: v1 is one function (runway = liquid cash / burn, at three burn levels). Configurable scenario objects come later if ever.
- Financial timeline, budget engine, sinking funds: later. Budgets only matter after two months of watching real numbers.
- Web API + "financial operations console": v1 has no web API. SQL views plus a single static HTML report generated by Python. A live dashboard is milestone 3 if the static report ever feels limiting.

None of this deletes ideas; everything cut is listed under Later so the schema can leave room for it without building it.

## Name

`purser`: the ship's officer responsible for the money. Fits the fleet (porter, cortex, tombstone, chateau), one word, unclaimed as a major project, works as a CLI name (`purser ingest`, `purser report`).

Alternates if it does not land: `coffer`, `bursar`, `tally`.

## Milestones

- M1 Ledger: ingest NFCU + Schwab CSVs, dedupe, normalize merchants, match transfers, categorize (rules first, LLM for leftovers, corrections become rules), balance check per account per month.
- M2 Reports: the four audit views (cash flow by month, habit spend, recurring charges, verdicts) plus runway at current/trimmed/essential burn, emitted as CSVs and one static HTML report.
- M3 Ongoing: monthly ingest routine, price-change and new-recurring detection, data-quality page, optional simple dashboard, optional SimpleFIN feed.
- M4 Investments and net worth over time, only if still wanted.

M1 and M2 are the whole original goal. Everything after is optional.

## Stack

Python 3.12 + DuckDB, SQL views for all analytics, pytest with fixture CSVs, no services, no containers required (it is a CLI against a local file), runs anywhere in the fleet. Rationale: one person maintains it, DuckDB reads CSVs natively and backs up as a single file to porter.

`.gitignore`: `data/`, `reports/`, `.env`. Secrets never in Git; there are no secrets in v1 anyway since nothing talks to a network.

## Where the export files go

Everything lands under `data/raw/`, one directory per account alias, and is never edited or renamed after landing. Adapters read from here; imports are idempotent so re-running over the same files is safe.

```
data/raw/
├── nfcu-checking/
│   └── 2026-08-28_2025-03-01_to_2026-08-28.csv
├── nfcu-savings/
├── nfcu-cc-<cardname>/          # one dir per card
├── schwab-checking/
├── schwab-brokerage/
│   ├── 2026-08-28_transactions_2024-08-28_to_2026-08-28.csv
│   └── 2026-08-28_positions.csv # balance/holdings snapshots welcome, same dir
└── schwab-ira/
```

Filename convention: `<download-date>_<range-or-kind>.csv`. The download date prefix means overlapping re-exports sort cleanly and dedupe handles the overlap. PDFs, if you ever pull older statements, go in `data/raw/<alias>/statements/` for archive and reconciliation only.

Account aliases are declared once in `config/accounts.yaml`; directory name must match the alias exactly. That registry is the join point for everything downstream.
